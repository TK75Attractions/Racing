# ペダル解除待ちの誤発生修正（2026-10-20）

## 原因

`TwoPlayerSerialInputSource`は別スレッドで受信したTELをキューに入れ、`Gmanager.Update`でセッションへ反映していた。一方、車両の`FixedUpdate`から使う`IsConnected`は、まだ反映していないセッションの最終受信時刻を現在時刻と比較していた。

遅いフレームの後は、通常の`Update`より先に物理更新が走る。100Hz通信で100msを超える処理停止があると、正常なデータがキューに届いていても切断と誤判定し、`PlayerDriveInputGate`が解除待ちを保持する。その後TELが反映されても、踏み込んだままでは解除されず「ペダルを離して再開」が表示される。

修正前の実PTY再現では、150ms停止で正常フレーム15件が待機、解析エラー0件にもかかわらず両者の入力が0、解除待ちがtrueになった。通信異常は再現条件に必要なかった。

## 修正

接続／鮮度の問い合わせ時にも、メインスレッド上で受信済みフレームを先に反映する。通常の`UpdateInput`も同じ処理を共有する。受信スレッドは引き続きbyte読み込みとキュー投入のみを担当し、通知の再入も防止する。

タイムアウト値と本当の切断後のペダル解除条件は維持する。各フレームの元の受信時刻を使うため、古いフレームがキューに残っていても通信復帰とは判定しない。
