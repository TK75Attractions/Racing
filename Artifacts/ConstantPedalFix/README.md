# Constant pedal・入力案内の修正（2026-10-20）

## 再現と修正

- 修正前はConstant pedalでもESP32とキーボードの両方を必須にしていた。ESP32接続済み・キーボードなしを想定したテストで失敗した記録が`before.txt`。Constant pedalはESP32だけ、W/S pedalはESP32とキーボードを必須とするよう修正。
- 常時踏み込みのため既存ゲートの解放待ちから抜けられない場合、SだけでなくF8のResume constant pedalで再開できるようにした。中立入力を既存ゲートが受け取ってから加速する。ポーズ中のゲートや生の入力値を読むだけでは再開を確定しない。再開操作後に通信途絶を検出した場合は再開要求を取り消す。
- 接続・準備・受信待ち・鮮度切れ・送信停止・通信形式不一致・キーボード不在を区別する。車選択・練習にも同じ理由を表示し、ポーズ・完走・リタイア済みの車や、自動運転へ切り替えた車の使っていない手動入力では接続案内を出さない。
- F8に状態表示、常時ペダルのRelease/Resumeボタンを追加。ハンドル試験の操作欄をパネル上部へ移した。静的HUD／練習フォントを351文字へ更新。

## 最終検証

Unity 6000.3.9f1、本番InputManager・RGP受信処理・PlayerDriveInputGate・car2.prefabのタイヤ物理／姿勢制御／PhysXを使用。

- `python3 Tools/TestP1SteeringInput.py`成功。実PTYの100Hz設定でP1ハンドル78度・ESP32ペダル0を送信し、Divisor 6.5で操舵12を入力。Unity Input SystemからすべてのKeyboardを取り外し、Constant pedal 65%で走行。1.6秒で16.84m移動、75.93度旋回、終了速度18.36m/s。位置・速度・姿勢は走行中に直接設定していない。
- 実際のF8用メソッドによる停止／再開、通常入力への復帰、P2維持、W/Sモードの合成とS優先、ポート閉鎖時の停止も確認。キーボード専用起動からの途中有効化も確認。
- 全状態のメッセージ、解放待ちの解除、0%／停止中の説明、ポーズ・完走後の非表示、入力切替後の未使用機器を参照しないことを検証。720pのHUDで文字が枠内に収まることを検証し、`notice-Ready.png`（解放待ち）と`notice-SerialPreparing.png`を描画・目視確認。
- Unityの通常再接続、P2自動運転切替、復帰・入力ゲート、操舵支援、着地報酬、追走、チューブ、結果表示の回帰検証に成功。
- `bash Tools/Validate-Rgp.sh`：98件成功。
- `bash Tools/ESP32Simulator/test.sh`：Swift 103アサーション、既存プロトコル18ケース、実PTY4シナリオ成功。READY待ちと鮮度切れが異なる接続状態になることも実受信処理で検証。150/350/650msの処理落ちで誤停止せず、本当の通信途絶では両プレイヤーを停止して解放待ちを維持。

主要結果は`validation.txt`。端末上のキーボード取り外し処理そのものが100msの通信鮮度制限を超え得るため、最終の実PTYテストでは取り外し後に新しいTELを待ち、明示的なF8再開を実行する。通信時間制限や通常ペダルの解放条件は緩めていない。

実ESP32のUSB接続と人による操作は未確認。ユーザーの「W/S pedalでも同じか」は未確認との回答なので、現場の症状の全てがキーボード必須判定に起因するとまでは断定していない。F8の状態表示で残る問題も切り分けられる。
