# 更新の進捗・起動直前の入れ替え・キャンセル（2026-10-31）

管理画面からの更新を常駐サービスが所有するよう変更した。既存Raceの接続や設定取得が途絶えても、ビルド進捗を表示し続ける。旧ゲームの120秒チェックへビルドを委譲しない。既存Raceの終了はビルド成功・出力確認後の起動直前に移し、失敗・キャンセルでは既存Raceを終了しない。

`decision` ファイルの排他的作成で、キャンセルとアプリ切り替えの同時実行を防ぐ。キャンセルは現在の要求IDだけに適用し、所有するビルド子プロセスとworktreeを片付ける。Editorはプロセスとして終了せず、対応したゲームのAPIでPlayのみを停止する。引き継ぎ要求にはセッションと実行中のビルド証跡を要求し、完了済みの要求では次のゲームを終了できない。

## 検証

- `Tools/OperatorUpdate/test.sh`：リレーの.NET 10ビルド、ホスト・ランタイム・実Gitワークフロー・別ポートの要求ガード・管理画面テストを通過。
- 実Gitワークフロー17件：最新mainの固定、未コミット変更とブランチの保持、二重実行、失敗、所有worktreeの後始末、既存の偽Raceがビルド中は残り起動直前に終了する順序、ビルド中キャンセルでビルドとコンパイラーの子プロセスが停止すること、出力不備・ビルド失敗では既存Raceが残ること。
- 要求ガード2件：更新と機器解放のセッション・要求証跡・古い設定変更番号の扱い。
- ランタイム：120秒超でもビルド／Playを維持、成功後だけ解放、未保存Editorを保持、更新が所有するメンテナンスの解除、終了済み要求の拒否。
- ホスト：macOSで実際に別プロセスグループへ分離した外部ジョブ、ブラウザ・Unityと独立した進捗／キャンセル、要求IDの一致、キャンセルの再送、切り替え確定後の拒否、再起動後の引き継ぎ。
- 管理画面の全テスト：72成功、失敗0、任意の診断ブラウザーテスト1件スキップ。ビルド中のUnity切断で設定エラーを表示しないこと、キャンセルの権限・要求ID・終了後の表示を確認。

ビルド／起動には代替実行ファイル、ゲーム終了の試験には専用の偽Raceを使った。実際の稼働中のRace・進行中の旧方式のビルド・Editorは停止していない。Windows PowerShellと本番Unityのフルビルドは、この検証では実行していない。
