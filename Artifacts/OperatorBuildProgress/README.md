# Unityビルドの遅延と進捗表示（2026-10-31）

## 調査

管理画面の要求 `20261031-224213-fc0b0dfdd1ef4c28beabd641ec972736` を確認した時点では、UnityとUnityShaderCompilerがCPUを使用し、build.logにはアセットのインポートが継続していた。worktreeに毎回新しいLibraryを作り、後始末で破棄するため、前回の読み込み結果を利用できていなかった。管理画面の状態も「Unityでビルドしています」の固定文言だけで、処理中の内容は見えなかった。調査中に要求はcancelledへ変わり、共通ロックも解除された。中止済みの要求を再開していない。

## 修正

- OS・Unityバージョン別にビルド専用Libraryを保持し、次の独立したworktreeで再利用する。キャンセル後も子プロセス停止後に保存する。作業中のEditorのLibraryは使わず、所有元とリンクを検証する。
- 6工程の完了数のバー、Unity内部の処理中バー、現在のアセット、経過時間、ログ更新からの秒数、最新の更新／Unityログを管理画面へ表示する。時間割合の推測値は出さない。
- 2分以上ログが更新されなければ状態を表示する。時間だけでビルドを強制終了しない。ログは上限付きで読み、操作者だけに返し、コマンド行トークンを伏せる。常駐サービス再起動後も最後の要求のログを参照できる。

## 検証

- `Tools/OperatorUpdate/test.sh`: ホスト・ランタイム・要求API・管理画面の検証を通過。キャッシュの境界を追加した最終の `test_update.py` は23件成功。新しいworktreeで再利用すること、キャンセル後の保存、所有元の相違、作業中EditorのLibraryへのリンクの拒否を確認。
- ホスト: 現在のアセット／工程の抽出、静かなログの扱い、巨大ログの読み取り上限、トークンの伏せ字、キャンセル時に完了バーにしないこと、再起動後の最終ログ、操作者以外にログを返さないことを確認。
- 管理画面の全テスト: 80件成功、失敗0、任意診断ブラウザーテスト1件スキップ。工程・経過・処理中の表示、HTMLを含むログをテキストとして扱うこと、旧サービスで誤ったバーを表示しないことを含む。
- .NET 10の本番リレー: 警告0・エラー0でビルド。
- 本物のUnity 6000.3.9f1を最小プロジェクトで2回実行し、異なるworktree間で実キャッシュを移動した。初回は24インポート・12.78秒、再利用時は1インポート・4.94秒。いずれも検証用アセットを正常に読み込んだ。時間はGit準備などを含む最小検証ワークフロー全体の時間で、本番Race全体のビルド時間ではない。Player出力と起動は代替処理を使い、本番Raceは起動・停止していない。

本番Raceの新たなフルビルドとWindows PowerShellでの実行検証は行っていない。旧要求の初回インポートで発生していたHDRP等のシェーダー警告を原因とするビルド失敗は、確認した範囲では認めなかった。
