**環境に関する訂正（同日追記）：この試走時、作業用コピーのコースFBXなどがGit LFSの参照ファイルのままで、元モデルの地形・チューブPrefabが正しく読み込まれていなかった。生成道路と車両の物理走行の記録は残っているが、元モデルの地面・壁を含む本来の環境での再現結果として扱わない。特に長時間の落下・復帰不能はその影響を含む。** その後ローカルの実データをSHA-256照合して復元し、バリア追加・2周設定の変更後の検証を `Artifacts/CourseSafety/` に別途保存する。このフォルダは変更前の3周の履歴であり、現在の再実行ではシーン設定の2周を使う。

## 方法と記録

- 実際の `SampleScene` と車両Prefabを使用。人間役2台はコース形状を読んでペダル・ハンドルを入力し、既存のCPU2台とレースする。通常走行で車両位置・速度・周回・順位を書き換えない。
- 通常設定は3周、CPU2台、全体上限360秒、人間先着後40秒。9回を自然なレース終了まで記録した。物理刻み約0.02秒を保ち、時間倍率8で実行した。
- 人間役はカーブで減速し、ジャンプ手前では目標24m/sへ加速する。P1/P2の直線目標は表のとおりで、実際の到達速度とは異なる。通常は異なる固定レーンを走り、ジャンプ手前で中央へ寄る。アイテムを狙って車線変更する戦略はない。
- アイテムなしの対照群では、ボックスとクリスタルだけを停止。加速パッド、ドリフト、CPU、接触とレース終了条件は有効。
- 復帰操作ありの回だけ、停止またはコース逸脱が4秒続いたら通常のリセット入力を送り、入力処理が消費するまで保持する。ゲームの自動復帰を追加したわけではない。
- ダッシュボードの外部公開処理を停止。シーン・Prefab・ゲーム設定を保存しない。

全体集計は [report.json](report.json)、比較用は [summary.csv](summary.csv)、全車の進捗グラフは [progress.svg](progress.svg)。各試走フォルダに `summary.json`、約0.1物理秒ごとの `trace.csv`、接触・取得・被弾・逸脱などの `events.csv` がある。Unityの通常ログは再実行時に `unity.log` へ出る。

## 通常速度での追加観測

時間倍率1で `split-fast-p1` と `items-402` を各90秒観測した。記録は [Realtime/report.json](Realtime/report.json)、[Realtime/summary.csv](Realtime/summary.csv)、[通常速度の進捗グラフ](Realtime/progress.svg)。両方とも観測窓の終了で記録を閉じたため、その時点の未完走車をDNFとして扱わない。

- **シールド被弾後の逸脱を通常速度でも確認。** `items-402` のP1は19.74秒に `(628.01, 16.35, 598.75)` でシールド被弾し、22.20秒に `(629.86, 16.29, 608.05)` からコース外へ出た。90秒の観測終了まで約67.8秒逸脱したままで、進捗は約241.9mに留まった。したがって、この問題は加速実行だけで生じたものではない。
- **落下車を追うCPUの停止も確認。** 同回のCPU1は路面上・進捗約433.4mに留まり、水平速度0.5m/s未満の継続が最大約21.3秒あった。CPU1はオイル被弾も1回あるため、停止の原因を追走制御だけに限定しない。
- **CPUの長時間落下は90秒では再現せず。** 通常速度の `split-fast-p1` でCPU1の逸脱は計約0.42秒、観測終了時の進捗約486m、復帰0回。加速実行で観測したジャンプ後の永続的な落下は、この通常速度観測では再現していない。開始時のCPU位相も違うので、完全に一致した再現試験ではない。

追加観測も2回とも記録完了、捕捉したゲーム実行時エラーは0件。通常速度での3周完走や、全体上限までの動作確認ではない。

## 優先する問題

### 高：妨害からの逸脱が、長い参加不能時間につながる

`items-402` のP1は物理時刻19.70秒、位置 `(627.43, 16.35, 598.70)` でシールド被弾。22.16秒にコース外へ出て落下し、終了まで約287.9秒コース外にいた。完了周回は0、手動復帰は0。記録上、被弾直後の約1.2秒だけで損失が終わらず、その後ほぼレース全体を失っている。

復帰操作ありの回では、P1のシールド被弾とP2のコンフューズに伴う逸脱後に計3回の復帰入力を使い、両者が完走した。ただし乱数の使用状況・CPUの絶対時刻の位相が違うので、別の回との差をリセットだけの効果として比較しない。

人間の自動復帰は無効で、ESP32の通常入力はハンドルとペダルのみ。復帰はキーボード操作のまま（`Documentation/ESP32SerialProtocol.md`）。スタッフ操作を前提にする場合でも、落下検知と復帰依頼が分かる表示が必要。改善候補は、実機から使える復帰入力、進捗を増やさない安全復帰、着地直後の妨害猶予、スピン後の向き・速度の調整。

根拠：`items-402/events.csv`、`items-402/trace.csv`、`items-reset-assisted/events.csv`。シールドの設定は `Assets/Items/CarItemEffects.cs`（入力停止1.2秒、既定1.5回転、水平速度45%保持）。

### 高：ジャンプ中のCPU同士の接触後に、復帰しないケースがある

`split-fast-p1` のCPU1は31.16秒に離陸し、31.58〜31.80秒にCPU2との接触通知が続いた。31.82秒の速度は約9.52m/s。いったん路面に触れた後、34.98秒に横へ逸脱し、約267.2秒コース外のまま終了した。CPU1の復帰回数は0。接触通知には同じ時刻の複数通知があるため、通知数を独立した事故件数とは数えない。

別の `both-slow` ではCPU2が13回復帰し、コース逸脱時間が約76秒だった。復帰できるかだけでなく、同じ場所で失敗を繰り返さず再走行できるかを確認する必要がある。

既存CPUはジャンプ手前で中央へ寄り、前方車に合わせて減速する。ジャンプ区間での進入間隔・着地点の混雑を考えた待避、最低離陸速度と接触回避の両立、復帰拒否理由の記録、繰り返し失敗時の別の安全点への復帰を検討したい。今回のログだけでは復帰が拒否された内部条件までは特定していない。

根拠：`split-fast-p1/events.csv` の31〜35秒、同 `trace.csv`、`both-slow/summary.json`。関連コードは `Assets/Managers/NPC/NpcRaceDriver.cs` のジャンプ・追従・`TryRecover`。

### 中：事故をしなくても、低速参加者が完走できない

直線目標12m/sの人間役2台は、ジャンプを知っていて手前で加速できる条件でも、停止・逸脱なしで2周DNFになった。目標27/13m/sの組も、速い側を入れ替えた両方で、低速側が1周完了の状態で先着後40秒の打ち切りになった。

コースは約1,829m。今回のスタート進捗はゴール基準より約106m手前なので、3周には進捗ベースで約5.59kmを走る。360秒に収めるには進捗の平均速度約15.5m/sが目安になる。初見の人の完走率を測った値ではないが、低速の参加者が安全に走っても終われない設定であることは確認できた。

展示の回転率を優先するなら現状の上限を維持し、初心者向けを2周にする、完走に代わる到達目標を明示する、残り距離による猶予を用意するなど、体験時間と達成感を一緒に調整したい。試走ログだけから最適な秒数は決めていない。

根拠：`both-slow/summary.json`、`split-fast-p1/summary.json`、`split-fast-p2/summary.json`。

### 中：停止後の再発進と、落下車を追うCPUの停止を確認した

`temporary-stop-p2` はP2の目標速度を45〜60秒に0へ変更。53.56秒には停止継続を記録し、再加速後の60.40秒に地下区間の `(495.79, -24.68, 231.69)` から逸脱した。その後約264秒コース外のまま0周DNF。この結果はコースを読む自動入力での一例で、人間の再発進一般が失敗することを示すものではないが、止まってから再び走る経路の追加検証が必要。

`items-402` では落下したP1を追うCPU1がコース上で約104秒、水平速度0.5m/s未満になり、進捗約441m・0周で終了した。落下車の進捗に追従し続けると、残った参加者の相手としても機能しなくなる可能性がある。

根拠：各試走の `events.csv`、`trace.csv`、`summary.json`。CPUの相手選択・速度補正は `NpcRaceDriver.cs`。

## バランス上の追加確認

- **取得機会が先行側へ偏る条件がある。** `items-401` はP2が9個、P1が4個取得。序盤のP1はボックスを取れていない。ボックスの6秒再出現と中央寄りの固定レーンが交絡するので、人間が左右のボックスを選ぶ場合も同じとは断定しない。順位別の確率だけでなく、後続が取得できる配置・復活時間を確認したい。
- **CPUへの妨害が多く、人間との逆転争いを直接評価できない。** 同回ではCPUに計6回のオイル被弾があり、人間は計1回。CPUも対象になる設計は動いているが、狙いたい人間へ作用しないことが分かる表示や距離による対象選択の検証余地がある。コンフューズに距離・視認制限はなく、アイテム確率は1位／2位以下の2種類のみ（`RaceItemTable.cs`、`Gmanager.TryGetItemContext`）。
- **CPUは9回・延べ18台すべてDNF。** 人間終了と同時にCPUを打ち切る仕様があるため、単にCPUが弱いという結論にはしない。ただし通常走行2回も両CPUがゴールまで約36〜84m不足しており、CPUが優勝する終盤が成立するかは別途確認したい。
- **同目標速度でもライン差が約12秒。** 対照群2回ともP2が約12秒早い。固定レーン・走行距離・ドリフト加速・CPU接触が異なるのでP2固有の優遇とは言えない。レーンや入力方針を入れ替えた比較が必要。

## コードから確認した別の問題（走行中の再現試験とは区別）

- `Assets/Managers/Gmanager.cs` の引数なし `ShowResult()` は、未完走でも `CreateFallbackResult(0, true, 1)` を作り、P1を完走登録する。ダッシュボード文書の「未完走プレイヤーはDNF」と不一致。今回の試走はこの入口で打ち切っていない。
- `Assets/TestAddForce/CarResetter.cs` の手動復帰は最寄り路面へ即移動し、他車の占有確認がない。CPU復帰には15m以内の他車と空間の確認がある。混雑場所での手動復帰による再衝突は未検証。

## 解釈の制限

- コースを知る自動運転であり、初見の人の認知・楽しさ・酔い・実機のペダルとハンドルの感触を評価したものではない。実機の2画面・シリアル・音声・入力遅延・描画負荷も未評価。車種・左右レーン・アイテムを狙う戦略の網羅試験ではない。
- 加速実行では、描画フレームで更新する順位・カメラ・公式時計と、物理ステップで更新する入力にタイミング差がある。公式時計の時刻は数秒単位で丸めて見る。360秒上限の観測値約363秒も、この更新粒度を含む。通常速度での追加観測は別フォルダに保存する。
- Unityの乱数seedは記録したが物理の完全再現は保証しない。CPUの競争位相は絶対 `Time.time` に依存するため、同じseedでも別の開始時刻では同じ展開にならない。
- `environmentContacts` は道路への通常着地も含む接触通知数。壁衝突・事故件数ではない。`takeoffs/landings` は開始時の非接地や短い浮きも含み、ジャンプ成功・失敗数ではない。
- `maxStall` は水平速度0.5m/s未満の継続時間。落下中も水平速度が減るため、地上で停止した秒数として一律に使わない。`position-discontinuity` は1物理ステップ8m超の移動の診断イベントで、高速落下も含む。ワープの証拠ではない。
- 新規の試走機能はEditor専用。製品ビルドに自動運転を追加しない。

## 再実行

Unityをこのプロジェクトで起動していない状態で、リポジトリのルートから実行する。

```sh
Tools/RunBalancePlaytest.sh
```

Unity上では `Racing > Playtest > Run Balance Agent Suite`。初回のアセット・シェーダー準備には時間がかかる。バッチ実行に `-nographics` や `-quit` を追加しない。車選択画面の初期化が描画を使い、終了はエージェントが制御する。

環境変数 `UNITY_EDITOR` でUnityの実行ファイル、`RACING_BALANCE_OUTPUT` で保存先、`RACING_BALANCE_TIME_SCALE`（1〜8）で時間倍率を指定できる。`RACING_BALANCE_RUN` は表の試走名（カンマ区切り可）で選択する。

短時間の通常速度観測の例：

```sh
RACING_BALANCE_OUTPUT=/tmp/racing-balance-realtime \
RACING_BALANCE_TIME_SCALE=1 RACING_BALANCE_WINDOW_SECONDS=90 \
RACING_BALANCE_RUN=split-fast-p1,items-402 Tools/RunBalancePlaytest.sh
```

`RACING_BALANCE_WINDOW_SECONDS` を指定した回は、時間窓終了時に記録を閉じる。レースを強制完走・DNFにせず、`termination=observation-window-ended`、`raceEnded=false` と記録する。9回の自然終了試走と混ぜて完走率を数えない。

保存済みログだけを再集計する場合：

```sh
python3 Tools/AnalyzeBalancePlaytest.py Artifacts/BalancePlaytest
```
