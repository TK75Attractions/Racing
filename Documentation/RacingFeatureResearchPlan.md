# レースゲーム比較調査・機能拡張計画書

作成日：2026年10月18日（日本時間）  
対象：このリポジトリの `SampleScene`、Unity 6000.3.9f1  
確認時点：`d6835ba`（作成前の作業ツリーに変更なし）  
位置付け：実装前の企画・開発計画。ゲーム本体の変更は含まない。

## 1. 提案の要点

**目指す体験は「初めてでも走り切れて、慣れるほど走行ラインと加速の使い方で競える、ハンドル・ペダル式の対面レース」。**

現在のゲームには、ドリフト加速、順位別アイテム、ジャンプ、坂、チューブ・壁面走行、車種差、CPUとの抜き合いまである。機能数を増やすだけでは、説明と調整の負担も増える。優先するのは、既存の仕組みを参加者が理解して使えること、その先に操作ボタンを増やさない駆け引きを足すこと。

推奨する順序は以下のとおり。

| 順序 | 実施内容 | プレイヤーにとっての変化 |
|---|---|---|
| 1 | 「体験／標準」のレース設定、ドリフトの短い案内、妨害の連続被弾対策 | 初見でも終わりまで参加しやすく、加速の仕組みが分かる |
| 2 | スリップストリームを単独試作し、採用を判断 | 前の車を追いかけること自体がチャンスになる |
| 3 | 指定ジャンプの着地成功フィードバック。加速報酬は別に検証 | 大ジャンプが「越えた」から「うまく決めた」に変わる |
| 4 | チューブ内のチャージラインを1区間だけ追加 | 既存の舞台に、このゲームらしいライン選択が生まれる |
| 5 | 実績に基づく結果の称賛、会場内タイムアタック | 順位以外の達成感と、もう一度挑戦する理由ができる |

**最初の開発範囲は順序1と、順序2の試作まで。** 大規模な分岐コース、常時変形するコース、オンライン対戦、車両破壊、複雑なパーツ育成は後回しにする。家庭用の継続プレイも狙う場合は、順序5の優先度を引き上げる。

## 2. 調査方法と前提

### 2.1 確認したもの

- 現行コード、保存されたシーン設定、プロジェクト内の仕様書・試走記録・既存キャプチャ。
- 市販10作品の公式サイト、公式マニュアル、開発元・販売元の説明。比較対象はカート、アクション、タイムアタック、シミュレーション寄りの作品から選んだ。
- 「他作品にある機能」と「本作への導入提案」は分けて記述した。後者は本作の入力・運営・物理構造を踏まえた設計判断であり、導入効果が実証されたものではない。

今回はUnityを起動して新しい実走テストをしていない。保存済みの自動試走は人間の理解度・楽しさの評価ではなく、記録時点のコースやリビジョンも異なる。Web情報は調査日に確認できた記載範囲に限り、各作品の全機能や最新パッチを網羅するものではない。

### 2.2 利用場面の仮定

リポジトリ名、2人用実機入力、参加者ごとの準備タイマー、運営ダッシュボードから、**模擬店・展示などで初見の2人が短時間遊ぶ用途を主軸**と仮定した。開催日、開発人数、残日数、参加年齢、希望する回転率は未確定。これらによって優先度と日程は変える。

体験全体の時間は「車選択＋練習＋相手待ち＋レース＋結果＋交代」で評価する。現在の車選択30秒・練習60秒・レース上限360秒を単純に足して、1組の所要時間と断定できない。2人の準備開始が独立しており、タイトル待機や交代時間もあるためである。

### 記録から分かる改善の入口

保存済みのレベル別試走では、初心者役対上級者役の条件で、初心者役は猶予180秒でも1周完了のDNFになっている。一方で路外時間は0秒で、単純に「落ちるから完走できない」とは判断できない。2周の距離、巡航速度、先着後の猶予を合わせて検討する必要がある。[試走報告](../Artifacts/SkillPlaytest/README.md)

これは既知コースを走る入力モデルの結果であり、実際の初心者の完走率ではない。記録のリビジョンは`c86376c`で、今回のHEADより前。現行版で人による基準試走を取り直す。

### 比較から見える本作の立ち位置

本作の特徴は、**身体で操作する2人の対面体験と、学校マップ・チューブ・壁面の立体コース**にある。家庭用ゲームのように操作の種類や長期育成を増やすより、「前の車を追う」「曲がって溜める」「ラインを選ぶ」「飛んで着地する」を、現在のハンドル・ペダルで連携できる方がこの特徴を伸ばせる。

一方、市販作との差として優先して埋めたいのは、初見者と経験者の遊び方の分離、操作成功を理解する手掛かり、順位以外の達成感、反復プレイの目標である。

## 6. 推奨機能の仕様案

以下の秒数・距離・加速量は**初回試作の仮値**。既存実装の値や、市販作と同じ値だという意味ではない。

### A. 体験／標準のルールプリセット

**目的：初見者にも終点を見せつつ、運営が毎回同じ条件で始められるようにする。**

| 設定 | 体験プリセット案 | 標準プリセット案 |
|---|---|---|
| 周回数 | 全車1周 | 現行の全車2周 |
| レース上限 | GOから180秒を仮設定 | 現行360秒 |
| 人間先着後の猶予 | 基本40秒、ペースにより最大90秒、全体上限内 | 現行の基本40秒～最大180秒、全体上限内 |
| アイテム | シールド・ロケット中心。左右反転なし。最初はオイルも無効で比較 | 現行4種を基準にCの保護を評価 |
| CPU | 現行2台を基準に維持 | 現行2台 |
| 操舵・ペダル | 初期は現行の操作と安定補助を維持 | 現行を維持 |
| 走行案内 | ジャンプ予告に加え、初回ドリフトの短い案内 | 未習得時のみ案内する設定 |

体験プリセットでも完走が難しければ、締切だけ延ばす前に、速度・ジャンプ到達・案内理解・停止理由を分けて調べる。最高速を一律に下げるとジャンプに届かなくなる恐れがあるため、速度制限を最初の施策にはしない。

レースの周回・締切・アイテム規則は全員共通。片方1周・片方2周の対戦は通常順位に混ぜない。将来プレイヤー別の操舵支援を加える場合も、支援の使用を明示し、記録を分ける。

運営はタイトル待機中に選択し、GOまでに設定を固定する。レース中の変更は受け付けない。タイトル、練習終了案内、カウントダウン、HUD、結果、ダッシュボードが同じ設定値を参照する。リトライは同じプリセットを引き継ぎ、「次の組」では会場の既定値へ戻す。

### B. 既存ドリフトを使えるようにする

現在の基礎練習は加速・操舵・停車まで。ドリフトを必修の長い課題として追加する前に、走行中に短い案内を試す。

1. 広い通常コーナーで、未成功の人に1回だけ「曲がってためる」を表示。
2. 蓄積が一定量以上になり、出口に十分な路面があるとき「少し逆に切って加速」。必要ならハンドル図を添える。
3. 実際に解放ブーストが成立したときだけ「ドリフト加速！」と短い音を返す。

案内は常時表示せず、ジャンプ予告・切断・ペダル解放案内を優先する。逆操舵を強く促して事故を起こさないよう、推奨区間を指定する。文字・図・音を併用し、火花の色だけで段階を区別させない。

「初心者には最初から完全自動で解放する」は別実験とする。現行の中立保持・逆ハンドル解放を一度に変えると、車種差、クリスタル、チャージ表示まで再調整になるためである。

### C. 妨害を受け続ける時間を制限する

現行のシールド・ロケットによる防御、復帰後2秒保護は維持する。その上で、**妨害が終わった直後に0.8–1.2秒程度、新しい妨害を受けない期間**を試す。

- オイル、反転、スピンの被弾を同じ受付判定で扱う。
- 効果中の再被弾による持続時間の更新・別効果の重なりにも上限を設ける。終了後保護だけでは、終了しない連鎖を防げない。
- 初期案は妨害開始から最長3秒で通常操作へ戻し、続く1秒を保護。既存ロケット等の状態を誤って解除しない実装にする。
- 保護中は他車を飛ばしたり、恒久的なシールド報酬を得たりしない。見た目は小さい明滅・アイコンで区別する。
- ジャンプ踏切手前・空中での新規反転／スピンは、無効化するか対象を選び直す。安全区間に入った瞬間の遅延発動は予告なしでは行わない。

抽選率を先に大きく変えず、「何秒操作を失ったか」「同じ人に集中したか」「理解できたか」を測る。左右反転が初見に伝わらない場合は体験モードから外す。アイテムの数を増やす判断はこの検証後に行う。

### D. スリップストリーム

**目的：前の車を追う行動に報酬を与え、直線で抜く機会を作る。** マリオカート ワールドの追走加速から着想し、次のように本作向けに絞る。

- 前車の後方6–20m、横ずれ2.5m以内、速度8m/s以上で約0.9秒追走すると成立する仮設定。
- 世界座標の距離だけで判定せず、同じ進行方向・近いコース区間・同じ高さ／走行面にいることを確認。立体交差の上下、チューブの反対面、壁越しでは成立させない。
- 初期は通常の直線区間限定。ジャンプ手前45m、空中、急カーブ、ロケット中、復帰直後は停止する。
- 成立後は0.7秒程度の小加速を自動付与。風の線と短い音で「追走→加速」の因果を伝える。
- 同じ相手からの再成立には約3秒の間隔を置く。接触するまで近づくことを求めない。
- 人間は人間・CPU双方を追走対象にできる。CPU自身への加速付与は最初の試作では無効とし、非対称な支援であることを企画・設定に記録する。競技モード採用時は同条件化か無効化を選ぶ。

既存CPUには進捗差による速度調整がある。追走を成立させるためにCPUが不自然に減速しないか、人間が抜いた直後にCPUが急加速して取り返さないかを比較する。大きく離れた人を救う機能ではないため、完走支援の代用にはしない。

### E. ジャンプ着地の成功フィードバック

最初は、コース側で指定した踏切→空中→着地の順序を正常に通ったら「着地成功！」を出す。滞空時間の長さだけで報酬を決めない。

加速報酬を試す場合は、着地後に2本以上のタイヤで安定接地が続き、進行方向が大きくずれず、着地先が空いていることを条件にする。仮の報酬は0.5秒の小加速。着地直後がカーブなら加速せず通知だけにする。

段差の小跳ね、壁衝突、転落、リスポーン、ロケット自動操縦の飛行では報酬を出さない。同じジャンプは1周に1回まで。失敗に追加の減速・再試行義務は付けない。まず「成功の意味が伝わるか」を確認し、その後に加速の有無を比較する。

### F. 本作固有の見せ場：チューブ内チャージライン

**既存の1区間に「中央の走りやすいライン」と「左右の少し狙うライン」を設ける。** 左右のラインを正方向に連続通過すると、ドリフトチャージを少量得る。F-ZERO 99の収集による経路選択を、本作の既存チャージへ応用する案である。

- 第1版は、実際に走れる路面上の左右帯で作る。壁上部を必須にしない。
- 上級者向けの高い壁面帯は、接地・視認性・復帰が確認できた後に別版で試す。
- 1区間あたりの報酬は正規化チャージ0.25程度から調整。得た分は現行と同様に逆操舵で解放する。
- 同じ区間は1周1回。往復、復帰、停止し続ける行動では再取得できない。
- 既存クリスタルは満チャージまで増やせるため、近接配置すると新しい帯が無意味になる。区間内の報酬配置を一体で見直す。
- 相手が先に通過しても、自分の1回分は取得できる方式を初期案とする。共有クリスタルの奪い合いとの差も明示する。
- CPUは第1版では狙わず、中央を走る。CPUも使う版は別の難度として評価する。

成功すれば「追走してチューブへ入る→左右のラインを狙う→出口でチャージを解放」が、このゲームならではの流れになる。1区間で成立しなければ増設しない。

### G. 結果で実際の成功を称える

順位・タイム・DNFを表示した上で、プレイヤーごとに実際に達成した1件だけを追加する。

| 表示例 | 集計根拠 |
|---|---|
| ドリフト加速 3回！ | 一定量以上のチャージを実際に解放したイベント |
| 大ジャンプ成功！ | Eの有効な着地成功イベント |
| 追い上げ成功！ | 前半より上がった確定順位。復帰・周回境界による瞬間変動は除外 |
| チューブのライン達成！ | Fの正方向・順序・周回条件を満たした通過 |

既存の順位メダルを別名で重複実装しない。成功イベントがなければ、走った周回や距離を表示する。DNFを完走として称賛せず、事実の範囲で参加の手応えを残す。

### I・J. 会場内タイムアタックとゴースト

本作は人間2人を前提にする箇所が多い。専用の1人モードには、片方の準備待ち、車生成、画面、音声、終了条件、再挑戦を分離する作業が必要。タイマーを表示するだけの小変更とは扱わない。

第1版は固定車両・固定ルール・1周、ランダムアイテムなし、CPUなし、ローカル保存。目標タイムは現行コースで人が試走して設定し、金・銀・銅は仮の数字で公開しない。名前入力の代わりに参加番号や任意の短い表示名を使えるようにする。

記録にはコース版、車両・物理設定版、ルールID、支援の有無を保存。復帰使用、区間未通過、運営終了、途中の設定変更を有効記録に混ぜない。会場ランキングと自己ベストは参加者の同一性が分からない限り分ける。P1/P2のスロット別ベストを、その人の自己ベストと呼ばない。

ゴーストは後から追加する。初期案は位置・回転・必要な見た目状態を約20Hzで記録し補間再生する。衝突・アイテム取得・順位には参加させず、コース版が違う記録は再生しない。物理が同じ結果を再現することを前提にした入力再生は採用しない。

## 7. 先に整理すべき実装上の依存関係

### 7.1 周回の有効性と分岐

現行の`LapManager.OnCarPassGoal`は、初回のスタートライン通過を区別した後、ゴール進入で周回を加算する。`OnCarPassCheckpoint`は現在処理を持たず、`GoalSensor`は主に複数Colliderと復帰直後の重複進入を防ぐ。

このため、**新しいショートカットやタイムランキングを追加する前に、逆走往復・ゴール再進入・路外復帰で周回を短縮できないことを検証する必要がある。** 今回、実プレイで不正周回を再現したという意味ではない。コードの受付条件から見た検証課題である。[LapManager](../Assets/Managers/LapManager.cs)、[GoalSensor](../Assets/TestAddForce/GoalSensor.cs)

競技用の記録検証は「正方向に所定区間を順に通過」「十分な走行進捗」「復帰履歴」を使う独立の検証器として設計する。体験モードに古いチェックポイント必須条件をそのまま戻さない。将来の分岐には、経路IDと合流点の進捗対応が必要になる。

### 7.2 加速の重なり

現行のドリフト加速と加速パッド、ロケットに、新しい追走・着地加速が重なる。各機能から独立して加速度を足し続けると、ジャンプ距離や曲がりやすさが変わる。

追加前に、加速源・残り時間・強度・許可区間をまとめる小さい管理層を設ける。以下を初期ルールにする。

- ロケット中は既存の自動操縦・ジャンプ速度制限を優先し、新規加速を受け付けない。
- ドリフトとパッドの現行挙動を基準に固定して測定し、新規加速分に上限を設ける。
- 追走・着地は同時なら強い方だけ。踏切前と空中では新規加速を止める。
- 切断、復帰、完走、結果、リトライで、付与待ち・蓄積・見た目をすべて解除する。

### 7.3 既存コンポーネントとの接続案

下記の新規名は設計案であり、現在存在するクラスではない。

| 追加する責務 | 接続する既存部分 | 分離する理由 |
|---|---|---|
| `RaceRuleSet`：プリセットと確定済み設定 | Gmanager、LapManager、RaceParticipantSession、HUD、DashboardBridge | 周回・締切の設定が各画面で食い違うのを防ぐ |
| `RaceGameplayEvents`：成功・被弾・復帰の通知 | DebugMover、CarItemEffects、CarResetter、結果UI | 表示と集計が別々の条件で成功認定しないようにする |
| `RaceBoostCoordinator`：追加加速の受付・終了 | DebugMover、AccelerationPad、CarItemEffects | 加速の積み上がりと状態の持ち越しを防ぐ |
| `SlipstreamController`：追走判定 | RaceParticipant、RaceCourse、LapManager | UIやGmanagerへ毎フレームの判定を詰め込まない |
| `CourseChallengeZone`：指定ジャンプ・帯の順序通過 | RaceCourse、TubeDriveSurface、接地情報 | 路面・進行方向・周回ごとの条件を共有する |
| `RaceRecordValidator`：記録用の通過検証 | GoalSensor、LapManager、復帰イベント | 体験モードの完走判定と競技記録の厳密さを分ける |

`Gmanager`は既に準備・車生成・進行・UI・音声との接点が多い。今回の機能追加で全面改修する必要はないが、新しい継続判定は専用コンポーネントへ置く。

### 7.4 演出と入力

案内の優先順位は、接続・ペダル解放 ＞ 復帰 ＞ ジャンプ予告 ＞ 重要な被弾 ＞ 学習案内 ＞ 成功の称賛とする。同時に大きな通知を複数出さない。新しい日本語は静的SDFフォントに含まれるか確認する。

ペダルの連打・踏み直しをアイテム発動に流用すると、加減速操作と混ざる。初期計画では新規入力を加えない。スタート加速Hも、既存の「ペダルを離してから入力を受け付ける」ゲートの後にのみ判定する。

日付指定の納期ではなく、着手後の実働目安。会場の本番が2週間以内なら、フェーズ1を優先し、新ギミックはDの試作結果を見て1つに絞る。

## 9. 検証・採用判断

### 9.1 人による試走

初回は初見者8–12人程度と経験者数人による探索的な評価を行う。統計的な効果の証明ではなく、説明不足や極端な失敗を発見する規模とする。年齢・経験・車種・機器条件を記録する。

- 初回プレイは、現行ルールと体験ルールのどちらかに割り当てる。初見の完走率は初回どうしで比較する。
- 新ギミックのON/OFF比較は別の再プレイで順番を入れ替える。同じ人の2回目が速くなっただけで、初心者支援の効果としない。
- 初心者同士、初心者と経験者、経験者同士を含める。
- 操作の説明が必要になった場面を記録し、終わった後に「何をすると加速したか」を本人の言葉で確認する。

### 9.2 暫定の採用基準

数値は計画上の目標であり、現在の実績値ではない。少人数の比率には人数も併記する。体験1周と標準2周のタイムを、そのまま性能改善率として比較しない。

| 指標 | 暫定目標・見る点 | 採用判断 |
|---|---|---|
| 初回完走 | 体験モードで8割以上を目安。介助あり／なしを分ける | 未達なら案内・距離・締切・ジャンプで原因を分解 |
| ドリフト理解 | 対象者の7割以上が自力で1回解放し、操作を説明できる | 成功回数だけ増えて理由が伝わらない場合は案内修正 |
| 妨害の公平感 | 連続操作困難時間、同一人への集中、理不尽さの回答 | Cの上限を守れても不満が増すなら反転等を外す |
| 追走の理解 | 発動した本人が「前車について行った結果」と分かる | 接触増・踏切事故・CPUの不自然さが出ればDを修正／不採用 |
| 着地・ラインの理解 | 報酬対象と理由が分かり、中央ルートでも走り切れる | 初見者が必須ルートだと誤解する場合は見せ方を修正 |
| 体験全体時間 | タイトル開始から次の組を受け入れるまで、中央値とp90を計測 | 目標回転率は会場側で決め、レース時間だけで達成扱いにしない |
| 再挑戦意欲 | 再挑戦希望と、その理由を記録 | 同伴者への遠慮や待ち行列も含めて解釈 |
| 実機負荷 | 2実モニター・実入力・実音声で60fpsを目標。基準との差も比較 | p95フレーム時間、入力遅延、音切れが悪化すれば演出削減 |

描画の既存記録にはM1・4台・別ターゲット出力での測定があるが、物理モニター2枚の本番構成を保証するものではない。[既存負荷報告](StandalonePerformance.md)

### 9.3 必要な技術検証

| 対象 | 必須の確認 |
|---|---|
| ルール | 1周／2周、独立準備、CPU先着、人間先着、猶予と全体締切、運営終了、リトライ |
| アイテム | 連続・同時被弾、保護境界、ジャンプ付近、対象完走、シールド・ロケットとの重なり |
| 追走 | 相手切替、横並び、逆走、周回境界、上下別路面、壁越し、空中、停止、切断 |
| 加速 | 低速／高速／3車種、パッド・ドリフト・ロケットとの重なり、踏切・着地・壁面 |
| 成功イベント | 1行為1回、復帰で再取得しない、往復で増えない、次レースに持ち越さない |
| UI | P1/P2分離、1280×720と1920×1080、日本語欠落、通知優先度、色以外の手掛かり |
| 記録 | 逆方向のゴール往復、区間省略、復帰、運営終了、コース版違い、保存破損 |
| 実機 | ハンドル中立・ペダル解放、USB切断・再接続、2画面、2音声出力、長時間の次組切替 |

既存の`BalancePlaytest`とレベル別試走を再利用し、新機能の不変条件を追加する。加速実行だけで完了とせず、通常速度の実コース走行と実機操作を確認する。ゴーストなどのない段階で、将来機能用の大規模な検証基盤を先に作らない。

## 10. 当面採用しない案と、再検討する条件

| 案 | 今の用途で優先しない理由 | 再検討する条件 |
|---|---|---|
| 手動アイテム保持・発射 | 操作用ボタンがなく、ペダル二度踏み等は運転と競合 | 操作機器を変更する、または自動発動の不満が明確になる |
| 耐久値・破壊・途中脱落 | 一度の失敗で体験が短く終わる。車両状態も増える | 経験者専用の別ルールを作る |
| 自由ジャンプ・グライダー | 空中入力・カメラ・復帰・到達判定を広く作り替える | 立体アクションを主目的にする |
| 常時変形・破壊される道路 | 固定中心線依存のCPU・ロケット・順位・復帰へ影響 | 複数経路を扱うコース基盤に投資できる |
| 大量の妨害アイテム | 学習量と被弾の不満が増える | 現行4種の理解と対策が十分に成立する |
| 天候によるグリップ変化 | 既にあるオイルと役割が重なり、ジャンプ等の再調整も必要 | 経験者向けのコース差を増やしたい |
| 多数CPU・オンライン対戦 | 描画・同期・運営の規模が変わる | 会場用途から家庭用・遠隔対戦へ目的を広げる |
| 長期の性能アンロック | 初回参加者と常連の条件が変わる | 継続プレイ主体に転換し、公平な対戦区分を用意する |

## 11. 実装着手時に確定する事項

現時点の推奨案はこの計画だけで試作に進められる。次の情報が分かったら見積もりと採用範囲を更新する。

| 未確定事項 | この計画で置いた仮定 | 判断への影響 |
|---|---|---|
| 本番までの残日数・担当人数 | 期限未定、開発者1人 | 2週間以内ならA・B・C中心に限定 |
| 参加者層 | 初見者を含み、小学生にも読める表示 | 左右反転、案内の長さ、試走対象を調整 |
| 1組の希望所要時間 | 未確定。まず全体時間を測定 | 周回、練習、待ち時間、結果表示を一体で調整 |
| 家庭用の継続プレイの比重 | 会場体験を優先 | 比重が高ければI・JをFより先にする |
| 本番Mac・表示・音声・入力構成 | 既存構成を継承 | 性能と遅延の採用基準を確定 |

当面の成果物は「体験設定で走り切れる」「ドリフトを理解して使える」「追走で抜く機会が分かる」の3点を確認できるリリース候補とする。チューブのチャージラインを次の看板機能として検証し、タイムアタックは別段階で育てる。
