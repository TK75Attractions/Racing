# レースゲーム制作・運営の総括と引き継ぎ

今年度のレースゲームは、無事に本番の運営を終えることができました。制作に関わってくれた人、筐体や機材について相談に乗ってくれた人、運営を支えてくれた人に感謝します。

この文章は、来年以降、縁日でゲームを作る人に向けた引き継ぎです。今年作ったものをそのまま再現するためだけでなく、同じところで悩む時間を減らし、自分たちの企画を考える時間を増やすために使ってもらえればと思います。

**1．スケジュール・感想**

**春：コンセプトと、実現できる範囲を決める**

3月には「皆で楽しめる、没入感のあるレースゲーム」というコンセプトを立てました。校舎を使ったコース、ハンドルやペダル、風や振動、プロジェクターによる演出、ARなど、かなり幅広く案を出しています。待っている人にも楽しんでもらいたい、という考えも最初からありました。

一方、3月末の時点でUnityや3Dモデルの担当者が少ないこと、ハンドル・ペダル・振動・ファンの検証が進んでいないことが課題として挙がっていました。振り返ると、作りたいものを考えるのと同じくらい早く、「誰が作れるのか」「実物で成立するのか」を確かめる必要がありました。

来年は、春のうちに一番不確かな部分を小さく試してほしいです。自作ハンドルを使うなら、完成した筐体を待たず、センサーの値で画面上の物を動かすところまで試す。複数人で遊ぶなら、仮のコースでもよいので、複数の入力と画面が同時に動くかを確認する。その結果を見て、企画の規模を決めると進めやすくなります。

**5〜7月：個々の部品を、一つの体験につなぐ**

5〜6月は、ハンドルの固定機構、筐体との接続、校舎モデル、画面遷移などを分担して進めました。ここで難しかったのは、それぞれの作業が進むことと、ゲーム全体が遊べる状態になることは別だという点です。

7月の記録には、モデルや入力の統合、最新版のブランチの確認、カメラの調整、ゴール判定、結果表示、開始画面への復帰などが並んでいます。ハンドルが動く、車が走る、校舎が表示される、という個別の成果だけでは、まだ一組のお客さんを迎えて次の組に交代できません。

模擬の目標は、「どの機能を増やすか」だけでなく、「お客さんがどこからどこまで体験できるか」で決めるのがよいと思います。まず、開始・操作説明・プレイ・結果・次の組の開始までを、見た目が仮でも一周つなぐ。その状態で他の人に遊んでもらえば、何を優先して直すべきかが分かります。

**夏〜9月：基本部分を固め、初めて遊ぶ人の反応を見る**

9月初めにも、マルチプレイ、画面遷移、管理画面、走行感、ハンドルの不具合修正などが主要な課題として残っていました。7月までに考えていたことが、そのまま7月中に完成したわけではありません。実装だけでなく、既存コードの理解、相談、統合、不具合の再現にも時間がかかります。

また、9月後半の反省では、道の分かりやすさ、直角カーブ、高低差、速度感、明るさ、音やエフェクトなど、遊ぶ人が感じる部分に多くの課題が挙がっています。ゲームとして進行できても、初見で迷わず、気持ちよく遊べるかは別に確かめる必要があります。

制作者はコースや操作を知っているので、説明不足や難しさに慣れてしまいます。テストでは先回りして教えすぎず、どこで迷ったか、どこで止まったか、何を見落としたかを観察してください。短い動画を残すと、担当者同士で問題を共有しやすくなります。

**10月〜本番：完成させる時間と、運営を練習する時間を分ける**

10月の制作資料には、複数画面や音声出力、入力の安定化、描画負荷、管理画面、メンテナンス表示など、本番環境に関わる調整が多く残っています。見た目や機能を作る時間とは別に、実際の機材で動かし続ける時間が必要です。

来年の目安としては、春に技術検証、5月の模擬で最小限の体験、7月の模擬で実機を使った一連の進行、9月の模擬で基本部分の完成と運営練習、10月は調整と安定化、という順番を勧めます。これは今年の達成実績ではなく、今年の経緯を踏まえた提案です。

本番前の一定期間は、新しい機能を増やさず、不具合修正と確認に使うと決めておくとよいです。追加したい案は必ず出てきますが、それを入れることで、すでに遊べていた部分が壊れることもあります。

制作を振り返って強く感じるのは、アイデアを実物にするには、分野をまたいだ調整が欠かせないということです。ゲームの挙動、ハンドルの感度、筐体の姿勢、画面、音がつながって初めて、一つの体験になります。担当ごとの成果を持ち寄り、全体を動かしながら改善する時間を、最初から予定に入れてください。

**2．技術面**

**ソフトとハードの境界を先に決める**

今回の構成は、UnityのゲームにESP32からハンドル・ペダルの入力を送り、P1・P2の画面と音声を扱うものです。ゲーム側とマイコン側で、入力の順番、値の範囲、左右の符号、校正方法、切断時の動作を合わせる必要があります。

「マイコンでは値が出る」「Unityではキーボードで動く」だけで終わらせず、実際の入力から車の動きまでを早くつないでください。キーボードでの確認は便利ですが、実機特有のノイズ、遅延、踏み心地、ハンドルの戻り方までは確かめられません。

ハンドルの記録には、高速に回した際のセンサーの問題や、姿勢推定の見直しが残っています。ゆっくり一度回すだけでなく、素早く切り返す、大きく回す、何度も操作する、再起動する、といった使い方で試す必要があります。配線も、机の上で通った状態と、筐体内に収めた状態では条件が変わります。長いI2C配線への懸念も議事録にあるので、実際の長さと配置で確認してください。

**遊びやすさを、物理の正確さと同じくらい重視する**

縁日のゲームでは、初めて触った人が短い時間で楽しめることが大切です。車の動きが自然でも、曲がれない、道が分からない、壁に引っ掛かって進めない状態が続くと、体験が止まってしまいます。

今回の記録でも、カメラ、コース誘導、曲面の壁、横転や停止からの復帰、ペダルやハンドルの感度が繰り返し課題になっています。正常に走れる場合だけでなく、逆走、コースアウト、壁への衝突、途中離脱からも進行を戻せるようにしてください。復帰のたびに制作担当者を呼ぶ仕組みだと、本番の運営が難しくなります。

練習や説明の長さも、実際に初見の人に遊んでもらって決めるとよいです。画面の文章だけで理解できるか、スタッフが何を補う必要があるかを一緒に確認してください。

**3Dモデルは早く取り込み、全体の見た目から整える**

校舎モデルは、細部を作るだけでなく、Unityへの取り込み、色や素材の設定、縮尺、道路との位置関係、当たり判定まで含めて確認が必要です。モデル単体で完成していても、ゲーム内では道がふさがる、見え方が変わる、処理が重くなることがあります。

5月の議事録にもあるように、まず建物の大まかな形、色、配置など、目につく部分から整えると、全体像と問題が早く見えます。早い段階で仮モデルをゲームに入れ、細部は順次差し替える進め方を勧めます。モデリング担当とゲーム担当で、縮尺・原点・受け渡す形式・更新方法を共有してください。

**本番のPC・画面・音声で確認する**

Unity Editorで動くことと、配布したアプリが本番機で動くことは、別に確認してください。複数画面の番号や配置、拡張表示、解像度、音声の出力先など、ゲームのコード以外にも動作を左右する設定があります。

実際に使うPC、モニター、USB機器、スピーカーをそろえ、両者の映像・入力・音声を同時に動かしてください。一回完走するだけでなく、何組も続けて遊ぶ、管理画面へ切り替える、再起動する、といった運営中の操作も試すとよいです。

Unity上で修正しても、すでに配布したアプリには反映されません。修正版は再ビルドし、どの版を本番機へ入れたかを記録します。直前の動作確認済みの版も残しておくと、更新後に問題が出たときに戻せます。

**共同制作とAIの利用**

7月の議事録には、どのブランチが最新版か、未統合の重要な機能がないかを確認するタスクがあります。最新版と、本番に使う版の置き場所は、全員が分かるようにしてください。シーンやモデルなど、同じファイルを複数人が触る作業は先に相談し、統合を模擬や本番の直前まで残さないことを勧めます。

AIに実装や調査を手伝ってもらう場合も、何を作りたいか、何が不具合か、何を確認すれば完成かは、人間同士で共有する必要があります。発想を担当する人と実装する人が一緒に画面を見たり、依頼文を考えたりすると、意図を合わせやすくなります。生成されたコードがコンパイルできても、実機で遊べることまで保証されるわけではありません。

**3．事務・運営**

**予算・購入・電力を制作と並行して進める**

5月末には予算を6万円に抑えたいという目標があり、7月の模擬までに必要なものを固めたいと話していました。ただし、これは当時の目標で、最終的な支出額ではありません。引き継ぐときは、計画時の予算と実際の購入記録を分けて残してください。

予算には主要部品だけでなく、ケーブル、コネクター、固定具、試作材料、予備部品も含めます。購入品は、品名・数量・金額・用途・購入者・立替精算の状況を一覧にし、領収書をまとめておくと後が楽です。借りる機材は、借用先と返却日も記録してください。

電力についても、PC、モニター、スピーカー、ファンなど、使う機器を早めに一覧にします。会場で使える電源や配置を担当者と確認し、延長コードの経路まで含めて準備してください。9月の議事録でも電力とお金は事務課題として残っていたので、ゲームが完成してから取りかかるつもりだと、終盤の作業が増えます。

**担当者と、作業の終わり方を明確にする**

「ハンドル担当」「UI担当」のような分担に加えて、次に何をするか、いつまでに終えるか、どうなれば完了かを決めてください。「センサーを調べる」より「センサーの値をUnityに送り、左右に動くことを確認する」の方が、進捗や困りごとを共有しやすくなります。

議事録には、担当者が未定の項目や、他の人への確認待ちの項目もあります。担当が空いた作業、相談待ち、購入待ちを会議で拾い、誰が次に動くかを決めるとよいです。調査結果も、調べた本人だけが知っている状態にせず、見つけやすい場所へ残してください。

**安全性と修理のしやすさを、筐体の設計に含める**

ハンドルは回すだけでなく、押す、引く、体重をかけるといった使われ方もします。5月の検討でも、さまざまな向きの力に耐えること、軸の固定、交換のしやすさが話題になっています。

椅子の安定、体格に合わせた位置、ペダルへの届きやすさ、指を挟む場所、露出した配線などを、実際に座って確認してください。外見を仕上げる前に、センサーや配線へ手が届くか、部品を交換できるかも考えておくと、運営中の対応がしやすくなります。

**管理画面とマニュアルを、制作担当者以外にも使ってもらう**

ゲームの開始、強制終了、プレイヤーの復帰、入力診断、音量調整、メンテナンス表示などは、運営スタッフが状況に応じて操作できる必要があります。管理画面やマニュアルも制作物として予定に入れ、最後に余った時間で作るものにしないでください。

本番前に、制作担当者以外の人へマニュアルを渡して、起動から終了まで操作してもらうのを勧めます。そのときに口頭で補った説明は、手順に追記します。「反応しないときに、最初に何を見るか」「どこまで自分で直し、誰に引き継ぐか」まで書いてあると、担当交代もしやすくなります。

**回転率は、乗り降りと復旧も含めて測る**

7月の開発計画には「2分／ペア」という目標がありましたが、これは実際の運営で達成した値を示すものではありません。来年は、プレイ時間だけでなく、案内、乗車、姿勢の調整、説明、結果確認、降車、次の組の準備までを通して測ってください。

列の案内、乗り降りの補助、開始操作、トラブル対応の役割を決め、混雑時にどこで時間がかかるかを確認します。待っている人に何を見せるかも、画面や筐体の配置と一緒に考えるとよいです。今年の構想にあった観客向けの演出も、制作時間と運営上の効果を見ながら優先順位を決めてください。

**4．後輩に残しておきたいもの**

引き継ぎでは、完成したデータに加え、次の人が動かすための情報もそろえてください。

- ソースコードと、本番で使った版が分かる記録
- そのまま起動できるビルド済みアプリと、必要な周辺ファイル
- Unity・依存ツールのバージョン、起動・ビルド・設定の手順
- マイコンのソースとファームウェア、配線図、通信仕様、校正方法
- 筐体の図面、部品表、分解・交換方法、組み立て時の写真
- 購入・精算・借用の記録と、機材の保管場所
- 当日の運営手順、確認済みの不具合、暫定対応、未解決の問題
- 使用した音楽・フォント・モデルなどの入手元と利用条件

今年のデータを使う場合は、最初に現状のままで起動し、どこまで動くかを確認してから変更を始めてください。過去の資料には、その時点の予定や、後から変わった仕様も含まれています。資料の記述と実際の画面が違うときは、使っている版を確認するところから始めるとよいです。

来年のゲームは、今年と同じものにする必要はありません。今年の記録や仕組みを足場にして、自分たちが面白いと思う体験を作ってもらえればと思います。早いうちに小さく遊べるものを作り、周りの人に触ってもらいながら育てていってください。
