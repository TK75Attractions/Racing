# レース管理ダッシュボード

`Assets/StreamingAssets/Dashboard/index.html` は Unity ビルドに同梱される画面で、同じファイルを GitHub Pages にも公開します。Unity の `RaceDashboardBridge` が `127.0.0.1:8765` で画面・状態・カメラ画像・シリアルログを配信します。ブラウザは USB シリアルポートを直接開きません。ESP32 のポートは引き続き Unity が占有します。

## FPS表示

ローカル管理画面とDashboard Relay経由の共有画面は、上部にUnity全体の現在のFPSと平均フレーム時間（ms/frame）を表示します。各プレイヤーのカメラやブラウザーのFPSではなく、UnityのUpdate間隔を `Time.realtimeSinceStartupAsDouble` で計測した約0.5秒ごとの平均です。一時停止中の `timeScale` に影響されず、処理の停止時間も含めます。追加の画面キャプチャやHTTPポーリングは行いません。

計測開始前・未対応のUnity・接続切断時は `--` に戻します。Firebaseの従来の遠隔スナップショット形式は変更していないため、Firebase経由ではFPSは計測待ちになります。

## 起動

1. Unity で `Assets/Scenes/SampleScene.unity` を開き、Play またはビルドを実行します。`Gmanager` がブリッジを自動起動します。
2. 同じ PC のブラウザで `http://127.0.0.1:8765/` を開きます。画面と API は同じ Unity プロセスから配信されます。
3. GitHub Pages の画面は、Firebase を設定すると別端末・外出先から状態監視に使えます。操作担当 UID には進行コントロールも表示されます。Firebase 設定が空の場合は設定待ちを表示します。
4. `UNITY 接続中` が表示されたら、状態・2人のカメラ画像・シリアル入力・人間とCPUの参加車両を確認できます。

`http://127.0.0.1:8765/` をアドレスバーで開くとローカルのダッシュボードを表示します。`http://127.0.0.1:8765/api/status` を開くと JSON で状態を確認できます。操作 API は許可されたダッシュボードからのみ受け付けます。

開始ボタンはタイトル画面、結果表示ボタンはレース中、再挑戦とタイトル復帰は結果画面で使えます。結果表示ボタンは `Gmanager.ShowResult()` を呼び、未完走プレイヤーは DNF として結果を確定します。ゲーム画面のプレビューは各表示のベースカメラを 640×360 JPEG として約2秒おきに取得します。GPU/CPU の負荷が増えるため、負荷が厳しい場合は `Assets/StreamingAssets/Dashboard/app.js` の画像更新間隔を調整してください。

シリアル監視は `InputManager` の処理済み行を最大80件保持します。キーボードデバッグモードではシリアルポートを使わないため、ポートは未接続と表示されます。`SampleScene` は現在キーボードデバッグモードなので、ESP32 を使う場合は、管理画面の「音量・出力・デバッグ」で入力モードを「P1/P2 実機（ESP32）」へ切り替えられます。

## 接続と公開

ローカル画面は同じ PC のループバックアドレスで配信します。GitHub Pages 自体はゲームデータを保存しません。Firebase 設定後は、Unity が HTTPS で Realtime Database の `/live` を更新し、公開画面は認証後にその値を閲覧します。操作担当 UID は `/control/request` に命令を送り、Unity が状態を確認して実行し、`/control/ack` へ結果を返します。映像はローカル画面のみです。

`.github/workflows/dashboard-pages.yml` は `main` に `Assets/StreamingAssets/Dashboard` の変更が入ると、同じファイルを GitHub Pages に公開します。公開先は `https://tk75attractions.github.io/Racing/` です。Firebase の接続は [具体的な設定手順](FirebaseSetup.md)、構成の根拠は [遠隔監視の設計](RemoteRaceDashboardPlan.md) を参照してください。

## NPCの状態監視

「参加車両・CPU状態」はP1/P2/CPU 1/CPU 2を順位順に表示します。順位、確定済み周回数、実速度、ゴール基準の累積進行距離を共有のレース参加車両から読み取ります。CPUには目標速度、追走相手（P1/P2）、相手との進行距離差、安全復帰回数、接触保護も表示します。差が＋なら相手が前、−なら相手が後ろです。距離差は周回込みで、最短の物理距離ではありません。

CPUの状態は停止／走行中／空中／後退復旧／接触後の譲り／停止・復旧待ち／完走／未完走です。安全復帰の回数は逆走操作や接触保護の回数を含まず、実際に安全確認後の位置復帰が成功した回数です。完走・未完走時は確定順位・完了周回数を表示し、CPUの完走だけでは人間のレースを終了させません。次の組では参加車両と復帰回数を作り直し、接続を失った画面では以前の行を消します。

ローカルでは既存の `/api/status` を1秒ごとに取得し、遠隔では既存のFirebase送信間隔（5秒）で更新します。追加カメラや画像取得は行いません。`players` は2人の入力用のままで、別の `participantCount` と `participants`（最大4台）で参加車両を送ります。遠隔のスキーマバージョンは1を維持し、旧Unityのデータも受け付けます。4KiBを超える場合はシリアル行を減らし、参加車両を残します。

遠隔へ反映する順序は、`Firebase/database.rules.json`の適用 → 管理サイトの配信 → 更新したUnityビルドの起動です。古いRulesは参加車両フィールドを拒否するため、先に更新してください。今回のコミットでは本番RulesやGitHub Pagesへの公開は行っていません。

検証はUnityの `Racing > Validate NPC Dashboard`（バッチは `-batchmode -nographics -executeMethod NpcDashboardValidation.Run -quit`）、画面の自動テストは `node --test Tests~/Dashboard/dashboard-ui.test.cjs`、Firebaseルールは従来通り `Firebase/tests` の `npm test` を使います。今回、Unityのコンパイルと状態・終了・リセット・Unicode込み4KiB制限、画面の4テスト、Database Emulatorの権限・CPUフィールド・異常値拒否・従来データ互換性を確認しました。実際の本番Firebaseへのアップロードは未実施です。

## RGP/1の日本語説明とエラー履歴

シリアルモニターの各行に、受信した原文と日本語の説明を併記します。TELは履歴へ蓄積せず、最新値欄でP1/P2それぞれの左右の累積角度・アクセル・ブレーキを説明します。装置の状態、校正・接続復旧イベント、設定、コマンド応答、エラー、診断文章にも対応します。古いTELや準備中のTELには、入力に反映しない理由を補足します。不正フレームを正常な入力として説明しません。

モニター上部の「エラー・警告の履歴」には、装置のWARN/ERROR/FATAL、解析失敗、バージョン不一致、コマンド失敗・応答タイムアウト、入力途絶、USB通信エラーを表示します。復旧後も履歴として残すため、表示中のすべての通知が現在も発生中とは限りません。Web監視との接続を失った場合は画面の古い通知を消し、再接続後にUnityからの履歴を表示します。

Unityは直近8件の通知を通常ログとは別に保持し、100 HzのTELでログが流れても通知を配信できます。ローカルは最大80行、遠隔は最大10行の枠内で通知を優先し、そのほかの枠を最新ログに使います。遠隔JSONが4 KiBを超える場合は、古い通知より新しい通知を優先して件数を減らします。既存のFirebaseスキーマとルールに対応し、ルール更新は不要です。

遠隔ログは従来どおり1行120文字までです。長いERRの末尾が省略されている場合は、取得できた重要度・対象・エラーコードの説明に「末尾が省略されています」と表示します。欠けた診断文章や入力値を推測しません。診断文章はUTF-8を1回だけ復元し、HTMLとして実行しません。

画面テストは `node --test Tests~/Dashboard/dashboard-ui.test.cjs` で実行します。実ブラウザーのサンプルデータによるレイアウト検査は、PlaywrightとChromeが利用できる環境で `node Tests~/Dashboard/serial-preview.cjs` を実行すると、`Artifacts/DashboardSerial/` にPC・スマートフォンの画像を保存します。Unityの `Racing > Validate NPC Dashboard` は、200件の通常TEL後も通知が残ること、直近8件の保持、ローカル80行・遠隔4 KiBの上限を検査します。

公開サイトには、Dashboardの更新をmainへ反映してGitHub Pagesを配信し、通知保持機能を含むUnityビルドを起動すると適用されます。

## 音量・出力・入力デバッグの変更

ローカルHTTP／Tailscaleの管理画面の「音量・出力・デバッグ」で、実行中に次の設定を変更できます。Tailscaleでは既存の操作担当者権限が必要です。Firebaseの公開画面は従来の配信スキーマを維持し、この設定操作には対応しません。

- ESCメニューと共通の音量：全体・BGM・エンジン音・効果音。両プレイヤーに即時反映し保存します。開いているESC設定画面も更新します。
- P1/P2別のオーディオ出力機器と再検出。「出力なし」も選べます。同じ機器を両プレイヤーに重複指定できません。機器IDで指定するため、再検出で一覧順が変わっても別機器を開きません。接続失敗時はゲーム側の状態とエラーを表示します。
- 入力モード：両者実機・両者キーボード・P1実機ハンドル＋W/Sペダル／P2キーボード。車選択・練習・走行中も変更できます。Inspectorの入力モード変更も次の更新で適用します。
- P1ハンドルテスト：通常・W/Sペダル・一定ペダル、一定入力の割合と停止／再開。一定ペダルはレース中のみ有効です。混合入力モードではP1の通常設定がW/Sになります。
- ゲーム画面のシリアルモニターとF8デバッグパネルの表示切替。F8パネル内の設定は、管理画面の「F8機能設定」からも操作できます。

入力モードを変更すると古い入力元・シリアル接続を破棄して構成し直します。車両とチュートリアルは保持中の入力ハンドルを通して新しい入力元を参照し、既存の中断状態と前進／後退の設定を保持します。切替後はペダルを一度離してください。シミュレーター有効時は従来の起動時PTY設定を優先します。入力・デバッグの選択は保存せず、次回起動時はシーンの設定に戻ります。

設定操作にもUnity起動セッション・状態・15秒以内の時刻・要求IDの重複抑止を適用します。設定の更新番号も検査し、別画面やESCから先に変更された場合は再確認を促します。切断・状態更新停止・閲覧専用の場合は操作を無効にし、旧バージョンUnityのスナップショットで値を推測しません。

検証は `node --test Tests~/Dashboard/dashboard-ui.test.cjs` と `sh Tools/DashboardRelay/test.sh`。後者は設定APIの権限・値検証・更新競合・出力の重複拒否、および実際の入力ハンドルと車両ゲートの切替・ペダル解放・一定入力の再開通知を確認します。`RACING_BROWSER_TEST=1` を付けるとChromeで設定の反映とPC／スマホの表示も検査します。常駐中継やUnityが8765/8766を使用している場合は、別の検証環境で実施してください。音声出力機器・ESP32の実機接続と実走の確認は別途必要です。

### F8機能設定

「音量・出力・デバッグ」の下部に、F8と同じ6個の機能スイッチを日本語で表示します。現在のON/OFFとONの件数を確認し、個別切替・「追加機能をすべてOFF」を実行できます。P2自動運転、CPU・追走ペース、操舵補助、ドリフト・着地・アイテム・演出・ランキング等を含みます。F8パネルと管理画面は同じ項目カタログと`RaceFeatureController`の変更処理を使い、どちらで変更しても状態を同期します。全OFFは音量・入力モードを変更しません。

プリセットは「標準（シーンの周回・制限時間）」と「体験（1周・180秒）」を選べます。適用中・次回のプリセット、現在の周回数、予約済みかを表示します。準備開始後は今回の周回・制限時間を固定し、変更は次のレースへ予約します。個別の機能スイッチは準備・走行中も即時反映します。

「P1手動・P2自動のテストレースを開始」はタイトル・結果画面で使用できます。車選択と練習を省略し、P2自動運転を有効にしてカウントダウンへ進む、F8と同じ操作です。画面遷移中やカウントダウン・走行中は受け付けません。

これらの操作も既存の操作担当者認証、Unity起動セッション・状態・設定更新番号・時刻の確認、要求IDによる重複抑止を通します。他の画面やF8で先に変更された場合は最新設定を確認してから操作し直します。切断時は以前のスイッチ表示を消し、閲覧専用・状態更新停止・旧Unityでは変更を無効にします。設定は今回の実行中のみ有効で、Firebaseの公開画面は従来の配信仕様を維持します。

検証：`Tools/Validate-Rgp.sh`でカタログの全項目・個別IDの検証とプリセットの予約処理、Dashboard UIテストで表示・同期・通信断・送信内容、DashboardRelayテストで個別切替・6項目OFF・予約・F8からの変更との競合・テスト開始の状態制限を確認します。ブラウザー検証は`RACING_BROWSER_TEST=1`で、6スイッチの表示、変更、全OFF、予約、テスト開始とPC／スマホのレイアウトを操作して確認します。

### 管理画面からキーボード相当の入力

ローカル／Tailscale管理画面の「プレイヤー入力」で、P1/P2別に「遠隔操作を開始」を押して操作します。入力モードを変更せず、そのプレイヤーだけ一時的に管理画面の入力を優先します。実機やキーボードが未接続でも操作でき、既存の車両・練習・ペダル解放ゲートを通します。

| 管理画面 | P1キー | P2キー | 動作 |
| --- | --- | --- | --- |
| アクセル・決定 | W | ↑ | 押している間加速。タイトル開始、車選択・結果の短押し／長押し操作にも使用 |
| ブレーキ | S | ↓ | 押している間ブレーキ |
| 左／右 | A／D | ←／→ | 押している間旋回。車種・カラー・結果の選択にも使用 |
| 復帰 | Space | ／・Right Ctrl | 1回の押下として復帰・練習の位置復元を要求 |
| スタート | Enter | Right Shift | タイトルで開始入力。通常どおり最初にペダル解放を待つ |
| ESC | ESC | ESC | 両プレイヤーの中断メニューを開閉 |

運転ボタンはマウス・タッチ・ペンに対応し、アクセルとハンドルなどを同時に押せます。フォーカスした運転ボタンではSpace／Enterを押している間も入力できます。復帰とスタートはクリックごとに1フレームの入力を送り、状態表示の読み取りや通信の重複で繰り返し実行しません。復帰は通常の`CarResetter`の安全な復帰処理に従い、送信受付だけで位置変更を保証しません。F8の切替は従来の設定欄で操作できます。

ESCメニューを開いている間は「走行に戻る」「前進・後退を切替」「スタート位置へ」「このプレイヤーを中断」をP1/P2別に使用できます。ゲーム内メニューと同じ処理を呼び、対象のメニューが閉じているとき・画面遷移中・操作対象の車両がないときは受け付けません。

「遠隔操作を終了」「自分の遠隔入力をすべて終了」、フォーカス喪失、ページを隠す／閉じる、通信途絶、レースの段階変更、入力モードの再構成で遠隔入力を解除します。ブラウザーは200msごとに操作の継続を知らせ、Unityは最後の受付から1秒で失効します。Unityの入力値を読む側でも期限を検査し、次の更新前に古いアクセルを使い続けません。終了後に元の入力へ戻る際は、踏まれたままのペダルで急に再加速しないよう一度の解放を待ちます。再操作時は開始ボタンを押し直してください。

入力はプレイヤーごとに一つの管理画面だけが取得できます。別画面の操作中は表示・受付を制限し、その画面の終了要求で他画面の入力を解除しません。各要求の順序番号で古い押下・再送を拒否し、終了要求は待ち行列を追い越して送信します。終了は同じUnity起動セッション・操作者の入力に限り、状態や時刻が変わった後でも受け付けます。操作担当者認証は既存と共通です。Firebase公開画面の配信仕様は維持し、この操作はローカル／Tailscale管理画面で利用します。

検証は`Tools/Validate-Rgp.sh`（保持期限・順序・占有・単発入力）、Dashboard UIテスト（権限・プレイヤー別送信・段階変更・通信待ち中の解除）、DashboardRelayテスト（実際の入力アダプターと車両ゲート、HTTP経由のキー入力・重複・失効・メニュー条件）。`RACING_BROWSER_TEST=1`ではChromeの実操作、ポインターキャンセル、ボタン外での解放、キーボード操作、フォーカス喪失、通信遮断、ESCメニュー、PC／スマホ幅も確認します。シーンの車両・ESP32実機での実走は別途確認してください。

復帰は遠隔操作の開始なしで実行できます。走行中／未完了の練習だけに受け付け、既存の安全な復帰処理を呼びます。実機・キーボードの入力元や他画面の遠隔操作の占有は変更しません。

## 2026-10-23：標準機能・機器診断・通知

F8と管理画面で切り替えるのは、体験向けアイテム、ステアリング補助、速いCPU、P2自動運転、校内の照明・植栽・街並み、手動プレイヤーに合わせたペース調整の6項目。その他の追加機能は標準で有効になり、旧版から全OFF要求が届いても無効化しない。P1のハンドル試験などの入力設定は管理画面に残す。

F8または管理画面の「P1自動 vs P2自動のレースを開始」で両者が通常の車両を入力で運転する対戦テストを開始できる。このモードは本日のランキングに記録しない。タイトル・結果から開始し、通常のレースへ戻ると解除される。

「機器・接続状態」のセンサーまたは「原因を調べる」を押すと、受信から確認できた事実、原因の候補、点検箇所を分けて表示する。操作権限があればGET_STATUS/GET_CONFIGを新しく照会し、待機中はSCAN_I2Cも行う。走行中はI2C検索を行わない。校正や入力設定の変更は診断中に自動実行しない。応答のないアドレスと対象機器は示すが、通信だけで個々の断線箇所は断定しない。P1ハンドル単体モード等で未使用のセンサーは故障扱いにしない。

診断画面はアイコン付きの短いカードで「原因と次の確認」を表示する。「確認済み」は校正・中央基準の未設定や今回の検索への無応答など、受信から確認した状態。「候補」は配線・給電などの推測で、破線のラベルで区別する。詳しい説明はカードを展開して読む。照会中の再表示でも開いた説明は閉じない。

接続の見取り図はESP32、I2C共通バス、P1/P2ハンドル、ADS1115、ペダルの関係を示す概略図。正常応答は緑の✓、異常は赤の!、準備・点検候補は黄色、未確認は?、未使用は灰色と文字で示す。診断対象を水色の枠で強調する。複数の使用中機器に異常があれば共通バスを黄色の破線で「点検候補」とする。USB断・古い応答では配下のセンサーを未確認にし、ペダルの正常表示には対象プレイヤーの正常範囲内の入力値も必要とする。

受信状態は小さなタイルにまとめ、通信の詳細と点検手順は下の「受信データ・詳しい点検手順」に残す。スマホでは1列表示、ダイアログ内のスクロール中も見出しと閉じるボタンを表示する。表示例と検証内容は [Artifacts/HardwareDiagnosis/README.md](../Artifacts/HardwareDiagnosis/README.md) を参照。

### iPhoneのホーム画面アプリへの異常通知

1. 更新済みDashboardをゲームPCで起動する。HTTPSのTailscale管理画面をiPhoneのホーム画面から開く（iOS 16.4以降）。以前のアイコンがSafariのブックマークとして開く場合は、更新後にホーム画面へ追加し直す。
2. 「iPhoneへの異常通知」で「通知を有効にする」を押し、iOSの受信許可を与える。初回の許可は端末でのタップが必要で、サーバーから代わりに許可できない。
3. 「テスト通知を送る」で受信を確認する。配送状態の「受付済み」はプッシュサービスの応答を示し、端末での表示を保証する表現ではない。

Dashboardリレーが画面の開閉と独立してUnityを監視する。使用中のUSB/IMU/ADS、入力途絶・不正値、未完了の校正・中央基準、レース進行中のUnity応答途絶を通知する。瞬間的な乱れを待ち、同一の継続障害は1回、全体でも最短1分間隔。正常状態を10秒確認してから再発を新しい障害とする。起動時の校正には猶予を置き、キーボード／両者自動運転中や意図的に使わない機器には接続警告を出さない。

購読先とVAPID秘密鍵はゲームPCのApplicationData/RacingDashboard/Pushに保存する（macOSの通常環境ではユーザーのLibrary/Application Support内）。`RACING_PUSH_DATA`で保存先を変更できる。秘密鍵と購読先はGit・Firebaseへ出さない。送信は標準のaes128gcm/VAPIDを使用し、失効した購読は削除する。受信にはゲームPCの常駐リレーとインターネット接続が必要。iPhoneがオフライン、集中モード中、通知を拒否している場合などは表示が遅延・抑制される。

[Apple/WebKitのiOS Web Push仕様](https://webkit.org/blog/13878/) / [採用ライブラリ](https://github.com/tpeczek/Lib.Net.Http.WebPush)

macOSで常駐版を更新するときは、`Tools/DashboardRelay`内で `dotnet run -- --update-service` を実行できる。既存のTailscale接続先・操作権限・購読鍵を保ち、コードと配信資産を更新して再起動する。初回導入は従来のInstall Dashboard Serviceを使用する。
