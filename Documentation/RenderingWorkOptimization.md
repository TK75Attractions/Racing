# 画質設定を変更しない描画処理の最適化

2026-10-21 / Unity 6000.3.9f1。

## 変更

- `CampusAtmosphereController` の景観を、全コース共通の1メッシュから96m単位のメッシュに分割。画面外の地域をUnityの通常のカリングで除外できるようにした。大きな地面の面は別バッチに分離し、その広いBoundsに近くの樹木や住宅が巻き込まれないようにした。元の四角形は境界でも分割・簡略化せず、全頂点・法線・三角形の向き・材質番号を保持する。各メッシュの実形状からBoundsを計算するため、地域境界での欠けや距離による突然の消失は発生しない。影の描画は通常のUnityの判定に任せる。
- `TireMarkRenderer` は位置・色・UVの頂点ストリームを分離。新しい区間の位置と色だけをGPUへ転送する。リングバッファの折り返し時は2範囲を転送し、上限を超える更新にも対応。未使用区間はインデックス数から除外し、クリア時も配列全体を消去・再転送しない。残せる4096区間、幅、色、UV、シェーダーは従来どおり。
- `LightningEffects` は稲妻本体も再利用し、幹・枝の描画オブジェクトと分割数別の座標配列を保持する。同じ規模の放電を繰り返したときのメモリ確保を減らす。再利用時は寿命・端点を更新し、終了時は追従先の参照を解放する。稲妻の形状計算、分割数、枝数、発光、ライト、雷鳴は変更しない。

解像度・影・LOD・パーティクル数・シェーダー・ポストエフェクトの品質設定は変更していない。既存の `RaceRenderBudget` の動作も変更していない。

タイヤ痕を1フレームに16区間追加する例では、位置と色の転送ペイロードは従来の262,144 bytesから1,024 bytesになる（4096区間×4頂点×16 bytes → 16区間×4頂点×16 bytes）。これはデータ量の計算であり、GPU時間やFPSの実測値ではない。

## 検証

`Racing > Validation > Rendering Work`、または次の方法で再実行できる。

```sh
/Applications/Unity/Hub/Editor/6000.3.9f1/Unity.app/Contents/MacOS/Unity \
  -batchmode -nographics -projectPath "$PWD" \
  -executeMethod RenderingWorkValidation.Run -quit \
  -logFile /tmp/racing-rendering-work.log
```

- 景観の面を浮動小数点のビット列で比較し、頂点・法線・三角形の向き・材質番号・重複数が完全に一致することを確認。負座標、地域境界を跨ぐ枝、回転した住宅、樹冠、環状の面、大きな地面を含む。
- 検証用の景観では全456頂点を保持し、ある視点でカリング対象に残るのは48頂点、メッシュは11地域に分離。実コースの頂点数やFPSを表す計測ではない。
- タイヤ痕の部分更新、リング折り返し、1フレームに上限以上の追加、古いデータの保持、色・UV、未反映データのクリア、クリア後の再追加をUnityの実Mesh APIで確認。
- 稲妻本体・座標配列の再利用、寿命リセット、分割数1〜7への変更を確認。
- 現在のソースからCore・ゲーム本体・Editorの3アセンブリを、インストール済みUnityとキャッシュ済みパッケージの参照を用いてコンパイルし、エラーなし。

このworktreeには一部のFBX・フォントなどがGit LFSポインターとして存在するため、Unityでの回帰検証は変更対象の3描画クラスと検証スクリプトをコピーした一時プロジェクトで実行した。実コースの画像比較、StandaloneのFPS・GPU時間、物理2画面での測定は未実施。景観の分割は描画対象の頂点を減らす一方、全地域が同時に見える俯瞰では描画バッチ数が増えるため、実機での比較では走行中とコース紹介の両方を確認する。
