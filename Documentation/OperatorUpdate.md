# 最新mainでビルドして起動する

Unityを手動で起動しておく必要はありません。次のいずれかを使います。

- 管理画面の「ゲームの更新 → 最新mainでビルド・起動」。Unity停止中も常駐Dashboardから操作できます。
- Mac: `Tools/OperatorUpdate/Update and Run.command`をダブルクリック。Windows: 同じ場所の`Update and Run.cmd`。
- ゲーム／Unity Editor／管理画面を開いているとき: **Ctrl + Alt + U**（Macは **Cmd + Option + U**）。Editorのメニューは`Racing > Update main, Build and Run`です。管理画面ではブラウザのタブにフォーカスしてください。

管理画面からはレース中も更新できます。既存のRaceはビルドが成功するまで終了せず、そのまま使用できます。ビルド完了時に試合中なら、試合全体の終了を待ってから切り替えます。片方のプレイヤーだけがゴールして結果を見ていても、もう片方が走行中なら終了しません。ビルド失敗やキャンセルでも既存のRaceを残します。ゲームの応答や設定値の取得とは独立して、常駐Dashboardがビルドの進捗とキャンセルを管理します。

Unity EditorはPlayしていない状態でも操作できます。ビルドが成功してから、ゲームだけを終了し、Editorは開いたままにします。新しい版のEditor内ゲームでは、起動直前にPlayだけを停止して機器を解放します。古いEditor内ゲームが引き継ぎに対応していない場合はPlay停止の案内を出し、Editorを強制終了しません。Editorのメニュー・ゲーム内ショートカットからの直接実行も、試合を止めずにビルドし、完了後に試合終了を待ちます。ビルド時間が120秒を超えたことだけで更新を停止しません。

## 更新の流れ

1. `origin/main`を取得し、取得したコミットを固定します。通信・認証・Unityの場所・空き容量に問題があれば、ゲーム終了前にその理由を表示します。空き容量の目安はAssets容量の3倍と64MBです。
2. `Builds/OperatorSource/<要求ID>`に独立したGit worktreeを作ります。現在のブランチ、未コミット変更、未保存シーン、ローカルmainは変更しません。ローカルmainが先に進んでいても更新できます。
3. 別フォルダーで音声プラグインとUnityアプリをビルドします。前回のビルド専用Unityキャッシュを再利用し、この間は既存のRaceを停止しません。
4. ビルド成功と出力の存在を確認すると「現在の試合終了を待っています」を表示します。タイトル・結果画面へ進むまでは切り替えを確定せず、この間もキャンセルできます。練習・カウントダウン・走行・ゴール演出中は待ちます。試合終了を確認したらメンテナンス表示で次の試合の開始を防ぎ、アプリ切り替えを確定します。既存のRaceを終了し、終了を待ってから `Builds/Operator/<要求ID>/Race.app`（Windowsは`Race.exe`）を起動します。Macでは新しいインスタンスを明示して開きます。Unity Editorのプロセスは終了対象にしません。
5. 更新用worktreeを削除します。過去のアプリとログは保持します。

管理画面には取得・ビルド・切り替え・起動の進捗とログの場所を表示します。ビルド中や入れ替え中にUnityへ接続できなくても、一般設定の「取得できません」という文言で更新状況を上書きしません。実際のビルド失敗は、ビルド側の理由とログの場所を表示します。

管理画面の更新要求は常駐プログラムが所有し、古いゲーム側の更新監視やタイムアウトへ処理を委譲しません。新しいゲーム／Editorへの起動引き継ぎには、現在のセッションと、実際にビルドが完了した実行中の要求を確認します。終了済み要求を使って別のゲームを閉じることはできません。

ログは`Logs/OperatorUpdate/<要求ID>/status.txt`、`update.log`、`build.log`、取得したコミットは`commit.txt`です。更新の重複はプロジェクト共通の`Logs/OperatorUpdate.lock`で防止します。PCの強制終了でロックが残った場合は、更新プロセスが動いていないことを確認してから、このロックフォルダーだけを削除してください。

## ビルドの進捗とログ

管理画面の「ゲームの更新」で、完了した工程のバー、Unityの現在の処理、経過時間、最後にログが更新された秒数、最新の更新ログとUnityログを確認できます。アセット読み込み中は対象ファイルを表示します。バーは取得・準備・ネイティブ処理・Unityビルド・切り替え・起動という6工程の完了数です。所要時間の割合ではありません。Unity内部の残量が確定しない工程は別の処理中バーで示し、根拠のない完了率や残り時間を出しません。

120秒以上ログが更新されなければ、その旨とキャンセル可能なことを表示します。長いシェーダー処理などでもログが止まる場合があるため、時間だけで正常なビルドを強制終了しません。ログ表示は末尾のみを上限付きで読み取り、管理画面を重くしないようにしています。閲覧専用の利用者にはビルドログを返しません。常駐サービスの再起動後も最後の要求のログを表示します。

## Unityキャッシュの再利用

毎回の独立したworktreeにはLibraryがなく、従来は完了・キャンセル時の後始末でインポート済みデータも失われていました。現在は `Builds/OperatorCache/<OS>-<Unityバージョン>/Library` にビルド専用のデータを保持し、次のworktreeへ移動して利用します。作業中のUnityプロジェクトのLibraryを移動・コピー・共有しません。所有元の異なるキャッシュや、Libraryへのシンボリックリンク／ジャンクションは拒否します。

初回は読み込みが必要です。以後は変更したアセットだけをUnityが再判定します。キャンセル・ビルド失敗時も、所有する子プロセスを停止してから途中までのキャッシュを保存します。元の作業ブランチ・未コミット変更と、一時worktreeを片付ける動作は維持します。UnityバージョンやOSが変わった場合は別のキャッシュを作ります。既に開始したジョブは開始時にコピーしたスクリプトで動くため、この方式は更新後の次の要求から適用されます。

## キャンセル

ビルド中は「ビルドをキャンセル」、ビルド後の試合終了待ちでは「更新をキャンセル」を使用できます。取得・準備・プラグインビルド・Unityビルドを停止し、この要求が作成した子プロセスと一時worktreeを片付けます。既存のRace・作業中のEditor・作業ブランチは終了／初期化しません。ログと生成済みの出力は確認用に保持します。

要求IDを指定してキャンセルするため、古い画面から別の更新を誤ってキャンセルしません。キャンセルとアプリ切り替えは、要求フォルダーの `decision` ファイルを排他的に作成してどちらか一方だけを確定します。切り替え確定後はキャンセルボタンを無効にし、既存Raceの終了途中で処理を止めません。キャンセル完了後には次の更新を開始できます。

この機能を導入する前に開始済みの旧方式の更新にはキャンセル機能がありません。進行中の更新と常駐Dashboardが同じプロセスグループに属する場合があるため、更新実行中の `--update-service` は拒否し、現在のビルドを勝手に停止しません。更新が完了してから常駐プログラムを更新してください。

新方式のMac更新はOS標準のPerl/POSIXで別セッションに分離し、常駐サービスと同じプロセスグループで終了されないようにします。要求フォルダーと共通ロックを使うため、ブラウザを閉じても継続します。常駐プログラムの再起動後も、実行中の要求を引き継いで進捗・キャンセル・起動前の機器解放を処理できます。

## 必要なもの・常駐Dashboardの更新

Gitクローン、GitとGit LFS、ネット接続とGit認証、対象バージョンのUnity Editorとライセンス・OSのビルドモジュールが必要です。MacはXcode Command Line Tools、WindowsはVisual Studioのx64 C++ビルド環境を使います。独立したUnityプロジェクトとアプリを生成するための空き容量も必要です。

標準以外の場所では`RACING_PROJECT_PATH`にGitクローンの絶対パス、`RACING_UNITY_PATH`にUnity実行ファイルを設定します。Macは`.app`のパスも受け付けます。Unity停止中は`ProjectSettings/ProjectVersion.txt`からバージョンを検出します。

既に常駐Dashboardを導入済みのMacでは、`Tools/DashboardRelay`で`dotnet run -- --update-service`を一度実行して補助プログラムも更新します。既存のTailscale経路・操作権限・通知登録は保持し、更新元プロジェクトの場所を記録します。新規導入は`Install Dashboard Service.command`です。公開の閲覧画面からは更新できません。

## 試合終了待ちの扱い

ビルド成功後の待機には時間制限を設けません。試合をメンテナンスで停止している場合は、解除して試合を終えるか、更新をキャンセルしてください。実行中のRaceがあるのにゲームAPIから応答がない場合も、終了と見なさず接続確認を待ちます。管理画面を閉じても常駐サービスが待機を続け、サービス再起動後も共通ロックから要求を引き継ぎます。

タイトル・結果画面で切り替える際は、ゲームの状態と設定の変更番号を確認してメンテナンスを要求します。直前に次の試合が始まっていた場合は切り替えず、その試合終了を待ちます。キャンセル／引き継ぎ失敗では、更新側が有効にしたメンテナンスだけを元の同じゲームセッションに対して解除します。既に運営者がメンテナンスにしていたものは維持します。

古いRaceでも、状態・メンテナンスAPIが使える版は常駐サービスから安全なタイミングを確認できます。対応しない版で終了を確認できない場合は待機を続けるため、更新をキャンセルするか、手動で旧Raceを終了してください。この動作には新しい常駐サービスと更新スクリプトを反映する必要があります。

## 新しい管理画面とRaceへの反映

管理画面の配信プログラムと、UnityでビルドするRace本体は別々に更新する。

1. この修正を含むソースを取得する。Macのターミナルで次を実行すると、既存の接続先・操作権限・通知登録を保持して常駐管理画面を更新できる。

   ```sh
   cd /Users/kenichirowada/LocalDoc/Code/Ennichi/Racing/Tools/DashboardRelay
   dotnet run --project DashboardRelay.csproj -- --update-service
   ```

   ビルド中の更新ジョブがある場合は、完了するか管理画面でキャンセルしてから実行する。`.NET 10 SDK` が必要。`--no-build` は古い配信ファイルを使う可能性があるため、ここでは指定しない。
2. 管理画面を再読み込みする。インストールした管理画面アプリ（PWA）も同じページなので、再読み込み、または終了して開き直す。再インストールは不要。管理画面はページ/APIをService Workerへキャッシュしない。
3. ペダルの決定条件やウィンドウ再配置の実処理を反映するには、Race本体を再ビルドして新しいアプリへ切り替える。管理画面の更新だけでは起動中のRaceは変わらない。
4. **「最新mainでビルド・起動」は `origin/main` が対象。作業ブランチだけの変更は含まれない。** 修正をmainへマージ・pushした後に押すと、その版をビルドして、成功後に旧Raceを終了して起動する。常駐サービスの更新は手順1を別途実行する。

main反映前にローカルの修正を使う場合は、このプロジェクトをUnityで開き、コンパイル後に `Racing > Build > Mac Player Windows` で `Builds/DisplayValidation/Race.app` を作る。ビルド成功後に既存のRaceを終了し、新しく作ったアプリを起動する。新しいRaceの接続後、「ゲーム設定 → 画面の配置」のボタンが有効になる。EditorのPlayではネイティブウィンドウを再配置しない。

## 検証

`sh Tools/OperatorUpdate/test.sh`で関連する回帰検証をまとめて実行します（.NET 10 SDK・Mono・Python 3・Nodeが必要です）。

`Tests~/OperatorUpdate/test_update.py`は実Gitリポジトリを作成し、最新mainの取得、未コミット変更・作業ブランチ・ローカルmainの保持、独立したビルド元、Unity停止時の起動、通信・ビルド失敗、二重実行防止、後始末を検証します。Unityとアプリ起動だけを代替実行ファイルに置き換えます。

`HostTests.csproj`はUnity非接続時の更新、権限、同一IDの再送、独立した進捗、キャンセル、要求IDの一致、切り替えの排他制御、完了後の機器解放、常駐プログラム再起動時の引き継ぎを確認します。`RuntimeTests.cs`は本番の更新コンポーネントをEditor APIの代替実装で動かします。`test_bridge_update.py`は一時ポートで本番の更新要求ガードと通常／クイックの設定検証を行い、実行中のゲームへ接続しません。管理画面のUI回帰テストは切断中の更新ボタンと専用APIへの送信も確認します。実際のUnityをビルドせず、ビルド・アプリ起動を代替実行ファイルに置き換え、専用の偽Raceだけを停止して順序を検証します。稼働中の実ゲームには触れません。Windows用PowerShell実行はWindows実機で確認が必要です。検証記録は [OperatorUpdateControl](../Artifacts/OperatorUpdateControl/README.md) に保存しています。
